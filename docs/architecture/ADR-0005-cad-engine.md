# ADR-0005: Deterministic parametric CAD engine

Status: proposed — Phase 4 foundation implemented; operational isolation exit gate open
Date: 2026-08-08

## Context

AccessForge needs personalized geometry while preserving reproducibility and safety boundaries. A language model can describe intent but should not emit arbitrary geometry or code. The project needs editable CAD artifacts, preview meshes, and template-level constraints.

## Decision

Use a typed, immutable DesignSpec and fixed CadQuery generators for the three
built-in template families. The compiler converts canonical SI lengths to the
CadQuery mechanical-CAD unit at one audited boundary. `trimesh` inspects only
the STL generated by the trusted compiler and creates the preview GLB. A
successful compiler result contains fixed-name STEP, STL, GLB, DesignSpec,
validation-report, plain-language README, and provenance artifacts.

Only a static allowlist may resolve `template_id@version` to a bundled,
repository-reviewed release and a fixed generator module. A release labelled
`reviewed_repository_only` is a repository trust boundary for the Phase 4
foundation; it is not a cryptographic signature, a physical-use approval, or a
safety certification. Community templates remain manifest-only until a
restricted declarative format and a reviewed release/signing process exist.
Uploaded/community Python, module paths, archive paths, or geometry text are
never executable inputs.

## Phase 4 compiler boundary

The implemented foundation invokes trusted compiler code in a short-lived
subprocess. It receives only a validated DesignSpec JSON document and returns
only a complete set of fixed artifact names. The parent worker accepts only a
complete result manifest and persists those artifacts under private keys with
recorded hashes.

The subprocess boundary deliberately provides the following defence-in-depth
controls:

- a disposable working directory, fixed output names, and a stripped execution
  environment without inherited credentials or proxy settings;
- a static template registry rather than plugin discovery or dynamic imports;
- no compiler database, queue, or object-storage calls;
- a wall-clock timeout, Unix CPU/address-space/file-size limits where the host
  supports them, and bounded native-library thread counts; and
- Python-level socket, DNS, and connection creation disabled in the child.

These controls are useful for trusted repository code and resource containment,
but they are not a replacement for operating-system isolation. In particular,
Python socket interception cannot block a native library or raw system call.

## Operational egress exit gate

The current Docker Compose and Render worker topology still provides the worker
with a normal container network. Therefore the project must **not** claim that
the compiler has enforceable no-egress isolation in a deployed environment.
Before that claim, or the Phase 4 operational exit gate, deploy the compiler in
a verified kernel/container/platform sandbox with outbound network denial,
read-only templates, a disposable writable volume, least-privilege credentials,
and demonstrable CPU, memory, wall-time, and output-size limits. Test that the
compiler cannot reach a public endpoint, private service, worker credential, or
another job's workspace.

Until then, repository-only template resolution and the subprocess safeguards
remain in place, but no real-user CAD compilation is enabled. The compiler may
run synthetic repository fixtures in automated tests only.

## Phase relationship

Phase 4 establishes reproducible geometry and limited software checks; it does
not establish a supported use, an R1 risk decision, manufacturing suitability,
fit, strength, comfort, or physical safety. Normal project DesignSpecs are
created as pre-risk R0 records, and the candidate route rejects them until
Phase 5 has recorded a current deterministic R1 decision with no unresolved
assumptions. Fixture compilation with an R1 test input does not bypass that
product gate. Phase 5 validation and Phase 6 controlled physical work remain
required before approval or export claims.

## Alternatives considered

- LLM-generated OpenSCAD/CAD code: flexible but difficult to bound, validate, reproduce, or secure.
- Blender Geometry Nodes: powerful, but less direct for precise parametric mechanical parts and backend headless operation.
- OpenSCAD-only templates: accessible and useful, but CadQuery provides a stronger Python API for typed domain integration and future geometry logic.
- Fully generic mesh generation: poor editability and weaker parameter provenance.

## Consequences

Positive:

- deterministic inputs and versioned template contracts
- editable STEP output
- clear safety review boundary at the template level
- testable geometry invariants

Costs:

- OCCT/CAD dependencies make Docker images heavier
- template maintainers need CAD and testing skills
- physical validation remains necessary and cannot be inferred from geometry alone
- a deployment-grade no-egress sandbox is still required beyond the subprocess controls

## Guardrails

- canonical SI units enter the compiler and conversions are retained in provenance
- no silent parameter clamping; a missing or out-of-range value fails before compilation
- only static repository-reviewed releases are executable
- complexity, CPU, memory, wall-time, and output-size limits apply at the supported layers
- record every repair, transform, version, seed, exact manifest, compiler fingerprint, and artifact hash
- software findings state what was not assessed and never certify safety
- failed critical validation blocks approval/export once the Phase 5/6 gates exist
